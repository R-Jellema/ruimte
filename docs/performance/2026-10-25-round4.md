# Startup and communication, fourth round

Measured on 2026-10-25 with Bun 1.4.2, macOS 27.2 and an Apple M4 Max. The reference is `282165813`. [Raw samples](2026-10-25-round4.json) include the retained changes and rejected build experiments. Every timing job ran without competing test or build jobs.

## Retained changes

### Interactive terminal output

The daemon used to wait 16 ms before sending the first output of every new burst. Idle output now goes immediately. Further output waits only for the remainder of that 16 ms interval. A continuously printing terminal still sends roughly one batch per interval.

The existing latency harness runs a daemon and a measuring client in separate processes. It measures a quiet terminal while another terminal prints continuously, and exercises both a local WebSocket and a real local ICE/DTLS/SCTP connection through werift. Each phase lasts five seconds, after a one-second warmup. Terminal echo has 20 samples per phase. Values below are medians calculated from the raw arrays.

| Terminal echo | Before | After |
| --- | ---: | ---: |
| WebSocket, otherwise idle | 18.27 ms | 0.51 ms |
| WebSocket, another terminal busy | 16.61 ms | 0.91 ms |
| Direct channel, otherwise idle | 18.81 ms | 1.49 ms |
| Direct channel, another terminal busy | 45.10 ms | 5.11 ms |

This measures delivery to the transport, before Chromium or terminal rendering. The direct-channel client is werift in Bun, not Chromium, and the network is loopback. Internet latency remains additional.

The busy WebSocket maintained 61.92 versus 62.03 MB/s, and 58 versus 59 output frames per second. The direct channel maintained 24.12 versus 24.08 MB/s and 1,611 frames per second on both versions, including its existing fair-share slices. These runs do not show a throughput improvement. Ping latency and the short chat-first-event sample did not consistently improve; no such gain is claimed.

The new fake-clock test failed on the previous code because the first byte had not been delivered. It now verifies immediate idle output, ordered batching of the following bytes, a new idle burst and flushing the tail at process exit. Existing attach, snapshot and detach tests still cover their separate lifecycle boundaries. The snapshot replay fixture now discards output preceding a replacement screen, as the client does. The detach fixture pins its clock and expects the immediate first frame followed by the buffered tail.

### Daemon command initialization

The HTTP command route statically imported every agent command definition. It now imports the registry only after authenticating the first command request. Method and token refusals stay ahead of the import. This changes the agent command layer, not canvas rendering.

| Process start through authenticated project list | Before | After |
| --- | ---: | ---: |
| Isolated lazy-import experiment, 9 runs | 92.72 ms | 83.21 ms |
| Final compiled version, 9 runs | 92.72 ms | 86.18 ms |
| 20 stored projects, 7 runs | 94.00 ms | 88.29 ms |

The project fixture is seeded through the real API before timed restarts. The first authenticated command now pays the registry initialization cost once; subsequent commands reuse the module. Help and dry-run tests verify the same command names and refusal rules independently of module evaluation order.

## The first launch of a new executable

The change above does not solve the roughly one-second first launch of a freshly created executable. The first observations in the compiled comparison were 854 ms before and 888 ms after. Repeated starts are the faster numbers in the table. No first-launch improvement is claimed.

Additional probes isolate the delay from daemon initialization:

- A minimal Bun executable with no daemon code took 583 ms on first execution and 18 to 21 ms afterward.
- Running only `--version` on a new daemon executable took 788 ms initially and 35 to 44 ms afterward. Its first JavaScript marker reported about 59 ms of process uptime.
- Reading the entire executable before running it still left a 783 ms first start. `codesign --verify --strict` before execution left 785 ms. Neither removed the delay.
- Three fresh copies of an already executed, identically signed daemon took 1,004 to 1,051 ms on first execution, then 34 to 39 ms. This is not specific to freshly generated JavaScript or a changed build id.
- A native C program without Bun took 125 ms on first execution and about 1 ms afterward. The same program with an unused 100 MiB data section took 625 ms initially and 2 to 6 ms afterward.

The shared first-use cost of native and Bun executables, and the gap before Bun's uptime marker, point to executable loading or execution validation on this Mac. The specific macOS service responsible was not traced. These locally ad-hoc-signed files are also not equivalent to a downloaded, notarized release. Apple's [Gatekeeper diagnostics](https://developer.apple.com/forums/thread/706379) describe the distinct signing and execution-policy checks; those checks are not bypassed here.

Smaller bytecode variants were rejected. Compiling only module-level bytecode reduced the file to about 79 MiB, but repeated daemon starts rose from about 83 to 115 ms. A one-level variant rose to about 95 ms. Identifier minification with retained function names reduced the file by about 3 MiB and kept repeated startup similar, but its first execution was still about 875 ms. None demonstrated the requested first-launch gain without a tradeoff in ordinary use.

## Transport processing

The new `apps/client/testing/performance/transport.ts` probe uses the production `LinkTransport`, socket adapter, dispatcher and schemas. In-memory handlers isolate serialization, transport and validation from disk work. The client and server of this small probe share a Bun process.

The initial local medians were 0.061 ms for a ping and 0.135 ms for a page containing 90 older assistant messages. This does not identify raw local request transport as a loading bottleneck. A separate synthetic case measures observed and unobserved events, including a 500-view project update; it verifies all subscribed deliveries. Payload validation was left intact. The terminal's deliberate buffering was the larger interactive cost.

## Validation and reproduction

The focused session/command tests, real terminal stream and remote peer integrations, packaged daemon test, full checks, unit suite and client/desktop build pass. The packaged test still opens a real daemon through Node, authenticates, opens a project and exercises the embedded search worker. No timing assertion is added to the ordinary unit suite.

Run latency measurements sequentially:

```sh
bun apps/server/scripts/measure-latency.ts --channel socket --seconds 5 --warmup 1 --out /tmp/socket.json
bun apps/server/scripts/measure-latency.ts --channel direct --seconds 5 --warmup 1 --out /tmp/direct.json
bun apps/client/testing/performance/transport.ts
```

The direct reference run loaded the original `session.ts` from `282165813` through a temporary Bun loader in both the harness and its daemon child. That loader did no work during the timed phases. The startup comparison used the production bytecode flags and the existing daemon harness:

```sh
bun apps/server/scripts/compile.ts --outdir /tmp/ruimte-performance
BENCH_RUNS=9 BENCH_DAEMON_BINARY=/tmp/ruimte-performance/ruimte bun apps/client/testing/performance/daemon.ts
BENCH_RUNS=7 BENCH_PROJECTS=20 BENCH_DAEMON_BINARY=/tmp/ruimte-performance/ruimte bun apps/client/testing/performance/daemon.ts
```

Keep the first sample when investigating a fresh executable. Running `--version` first warms that file and changes what the daemon's first sample means. The minimal-executable probes likewise used separate newly compiled files or fresh copies for each first-use comparison.
