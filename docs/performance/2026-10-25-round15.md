# Visible file preparation, fifteenth round

Measured on 2026-10-25 against Ruimte `6dc7886ef`, with ADE CORE `7b742950`, Bun 1.4.2, macOS 27.2 and an Apple M4 Max. [Raw samples](2026-10-25-round15.json) contain the staged experiments and a separate final comparison with three fresh headless Chromium profiles per case and version. Canvas rendering is excluded.

## Retained change

A restored file waited for the workspace code to load before asking the daemon to watch its directory. On macOS that request then waited 200 ms for the native stream to start. Reading before that barrier could miss a write, so reducing the wait itself would weaken correctness.

Visible ordinary files now prepare their parent-directory watches while the workspace loads. This includes project file views and restored loose file tabs. The reader takes over the same counted hold; it does not restart the watch. Hidden files, diffs, database tabs and chat-only workspaces add no preparations. Switching projects or closing a visible file releases unused preparations. Application feature code remains lazy.

The preparation subscribes to the existing project, document and tab stores. Stable input references avoid rescanning files on unrelated status updates. A small pure path helper avoids importing the file tree into the startup dependency graph.

| First content, median | Before | After |
| --- | ---: | ---: |
| Project file, local | 411.5 ms | 380.3 ms |
| Project file, 20 ms script response delay | 754.2 ms | 565.3 ms |
| Ordinary file tab, local | 409.6 ms | 378.3 ms |
| Ordinary file tab, 20 ms script response delay | 753.0 ms | 559.5 ms |
| Empty workspace, local | 187.2 ms | 189.8 ms |

The local file improvement is about 8 percent. With delayed script responses, overlapping the native startup barrier saves about 190 ms, or 25 percent. The empty workspace is effectively unchanged. Both versions request 96 JavaScript resources for the workspace. Decoded JavaScript at readiness grows by 1,526 bytes, from 7,031,433 to 7,032,959 bytes.

The response delay is a loopback HTTP fixture with no bandwidth or CPU throttling. It exposes asset-loading overhead, rather than predicting Electron's `app://` or a deployed HTTP/2 connection. The browser measurement starts after its own daemon is ready; daemon process startup is a separate probe.

## Readiness and freshness

Preparing watches earlier exposed two existing readiness weaknesses. A second request covered by a pending native watch previously resolved immediately. The server now returns the covering watch's startup promise. A pending child also follows a newer parent that takes over its native handle, and queued changes transfer to the parent.

On the client, opening or closing an ancestor and reconnecting can replace a descendant's readiness promise. Readers now inspect the current barrier rather than retaining the original one. They recheck it after both waiting and reading. Closing or switching a file while it waits cancels that request. A response from an old barrier is discarded. After an ancestor changes, descendant readers refresh once the replacement is ready.

The native 200 ms macOS wait is unchanged. A trial retaining child handles until parent readiness was rejected after a real watcher handoff lost an event. The retained implementation closes covered handles immediately, follows replacement readiness and refreshes readers after the replacement stream starts. It does not assume a client can infer whether the daemon successfully registered a native ancestor.

The final freshness fixture writes a unique marker through the authenticated daemon during watch startup, before the watch reply and before the application's first read. The first rendered text must contain that marker. All 24 freshness profiles pass, across project files, loose tabs, local responses and delayed scripts. Their timing remains comparable to the ordinary cases. The fixture first reads the daemon's actual metadata for the write's concurrency guard; an earlier fixture using raw fractional filesystem mtime was invalid and is excluded.

## Stages and validation

The file-view preparation was measured first, followed by loose-tab support. Both improve independently in the staged samples. The final matched batch uses the committed round-14 client and its original server watch implementation as the control. A temporary Bun loader supplies that server module without swapping working files.

A new server test fails on the previous code when a joined pending watch resolves too early. Three new DOM cases fail on the previous reader: replacement readiness, closing before readiness and switching paths before readiness. The retained implementation passes these and a fourth case covering a stale in-flight response. Seven preparation tests cover visibility, deduplication, cleanup, Windows paths, maximization and late loose-tab restoration. Existing watch lifecycle tests remain green.

Validation passes:

- Full application check and client/desktop build.
- 10,458 unit tests, 52,213 assertions, 964 files.
- All 395 DOM tests, 2,565 assertions, 97 files.
- Three native filesystem integrations, including a child-to-parent handoff during startup on macOS.
- Separate final compiled-daemon probe: 82.48 ms median through secret proof, ticket, protocol connection and first project list, with a controlled 300 ms CLI capability probe running in parallel. Its 150 ms budget passes.
- Separate 2,000-view sidebar probe: 1,365.22 ms main-thread CPU for 60 updates, below its 2,000 ms budget; keyboard navigation passes.
- Start-screen probe: 124.1 ms median, eight JavaScript requests, comparable to the previous 122.4 ms batch.

The delayed project-file and loose-tab cases pass a 650 ms median budget in all final three-profile batches. An additional old-build control fails that same budget for the expected timing reason. Timing jobs run sequentially and separately from builds and tests. Each fixture removes its own daemon, temporary projects and browser profiles. No running user application or project data is operated.

## Reproduce

```sh
BENCH_CONTENT=file BENCH_ASSET_DELAY=0 BENCH_RESTORE_RUNS=3 bun --conditions=source apps/client/testing/performance/workspace-load.ts
BENCH_CONTENT=file BENCH_ASSET_DELAY=20 BENCH_RESTORE_RUNS=3 BENCH_MAX_LOAD_MS=650 bun --conditions=source apps/client/testing/performance/workspace-load.ts
BENCH_CONTENT=tab BENCH_ASSET_DELAY=20 BENCH_RESTORE_RUNS=3 BENCH_MAX_LOAD_MS=650 bun --conditions=source apps/client/testing/performance/workspace-load.ts
BENCH_CONTENT=tab BENCH_WRITE_DURING_WATCH=1 BENCH_RESTORE_RUNS=3 bun --conditions=source apps/client/testing/performance/workspace-load.ts
bun --config=integration.bunfig.toml test --conditions=source ./apps/server/src/fs/watch.integration.test.ts
```

`BENCH_CLIENT_DIST` selects an existing separate client build. `BENCH_DAEMON_PRELOAD` allows a temporary control module loader in the fixture's own daemon. Ordinary runs need neither option. `BENCH_CONTENT=empty` checks the workspace without a visible file.
