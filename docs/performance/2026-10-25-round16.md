# UI responsiveness, sixteenth round

Measured on 2026-10-25 against Ruimte `ad5c3d186` and ADE CORE `7b742950`, with Bun 1.4.2, macOS 27.2 and an Apple M4 Max. The shared change is ADE CORE `d6aff76d`. [Raw samples](2026-10-25-round16.json) include intermediate trials, rejected experiments, final interleaved comparisons and separate startup regressions. Canvas rendering is excluded.

## Finding and retained changes

The actual command palette becomes expensive with a large project. In a 1,000-view fixture, typing and navigating its 1,005 options causes repeated catalog construction and React/DOM work. Settings typing in the same window is substantially cheaper. Reducing the fixture to 100 views brings its keyboard timing within the 50 ms budget, identifying list size as a load-bearing part of the reproduction.

The command catalog now stays separate from query filtering. Views, node jumps, projects and commands keep their row objects until their actual source changes. A typed query filters that catalog; it does not rebuild every row and icon. Renames and other catalog changes still update an open palette immediately.

Large catalogs also use the new optional `CommandPalette.VirtualList` in ADE CORE. The root retains all filtered values while only visible rows and a small buffer are mounted. Rows are measured, keyboard highlighting scrolls to its result, group labels stay accessible, and option positions describe the entire filtered list. The component uses [Base UI's supported virtualized autocomplete mode](https://base-ui.com/react/components/autocomplete#virtualized) and the TanStack version already used elsewhere in the workspace.

Ruimte enables this for command catalogs above 200 entries. That decision uses the complete catalog, so it does not repeatedly switch list implementations as a query narrows. Small catalogs keep the existing list. File browsing, file search, grep and chat search retain their existing renderers. There is no delayed query or stale-result selection path.

## Final matched comparison

Each case has three fresh browser profiles per build, ordered control/current/current/control/control/current. The control is the production client copied before any optimization. Every timing job runs separately from builds and tests. A real isolated daemon supplies the project; no agent turn runs.

The probe types `chat 99`, deletes it and navigates down 20 rows with trusted browser keyboard events. It verifies the exact query result count and checks that every selected row is mounted and in the viewport. A separate untimed smoke jumps from the first option to the final Settings action across the window boundary and runs it with Enter. The same profile also types and deletes `editor` in Settings.

The large slowed fixture uses about 63 percent less task time. Its measured p95 response falls about 77 percent. The normal-CPU keyboard measurement stays near its frame-pacing floor, while opening and CPU work improve. Chromium's 4x setting is a controlled CPU slowdown, not a measurement on an older physical computer.

The two-frame measurement starts at the trusted keydown timestamp and ends after two animation-frame callbacks. It includes input scheduling and subsequent rendering work, but is neither physical display FPS nor page INP. The raw Event Timing observer records only entries above its reporting threshold, so those records are not a complete latency distribution. First-opening and task-time samples are medians; p95 pools the keystrokes from each case's three profiles.

## Stages and rejected experiments

Catalog reuse alone reduced slowed task time from about 1,604 to 1,147 ms in its three-profile cohort. The first complete virtual-list trial then passed the 50 ms keyboard budget in all three profiles. The final table above is a separate matched batch using identical probes; its extra query and viewport audits make its CPU totals different from those exploratory stages.

Three alternatives were removed:

- Explicit indexes in the original fully mounted list gave too little consistent additional benefit.
- A manual memo around the command row did not improve on the compiler's existing subtree caching.
- An injected `content-visibility` row experiment reduced some frame samples but increased CPU work and left long tasks. No CSS from it remains.

A new component was added rather than changing every palette's default renderer. Its two exported prop types and compound part are deliberate additions to the API snapshot. Other consumers were inspected: the other shared apps do not use this palette API, so no call sites there change. The UI package now directly declares its virtualizer dependency. Ruimte's dependency pins and lockfile are unchanged; validation uses the local ADE CORE link, and no library release was published.

## Other responsiveness and startup checks

Settings typing does not show a consistent CPU improvement: in the large slowed fixture its median is 277.0 versus 279.8 ms. Opening Settings after the workspace palette varies more, including 53.4 versus 77.4 ms in that fixture. A separate cold-start comparison measures 22.4 versus 23.2 ms on normal CPU and 81.3 versus 88.4 ms with 4x slowdown; the slowed samples overlap. No Settings speedup is claimed.

The independent start-screen medians are 115.8 versus 119.8 ms normally, and 379.0 versus 391.3 ms under 4x slowdown. Both retain eight JavaScript requests. These small differences remain in the evidence; this round targets interaction cost after startup. The delayed first-file fixture measures 567.0 versus 559.2 ms and retains 96 workspace JavaScript requests. It passes its 650 ms budget. The 2,000-view sidebar also passes its existing 2,000 ms CPU budget and keyboard-navigation checks.

An additional old-build keyboard run fails the pooled 50 ms p95 budget for the expected timing reason. Three current slowed profiles pass. The full interleaved comparison passes all navigation and result-count checks in 18 profiles.

## Validation

- Ruimte check, client/desktop build, 10,458 unit tests and all 397 DOM tests pass.
- Two new application DOM cases protect cross-group navigation, filtering, live renames and opening the selected file.
- ADE CORE check, full package build and documentation build pass; its default suite passes 7,311 tests with 287 skipped.
- A separate UI DOM test passes 11 assertions for bounded option mounting, filtered groups, accessible positions, Enter and empty results. It supplies viewport geometry because the DOM runner has no layout engine; real scrolling is checked in Chromium.
- The packed UI package passes source/default export resolution, source/declaration consumer typechecks and Node/Bun execution. Its new runtime and type exports are included.

No wall-clock budget was added to ordinary unit tests. Fixtures remove their own temporary projects, daemon and browser profiles. No user application or user data is operated, and nothing is pushed.

## Reproduce

```sh
BENCH_VIEWS=1000 BENCH_CPU_RATE=4 BENCH_RESTORE_RUNS=3 BENCH_MAX_P95_MS=50 BENCH_NAVIGATION_SMOKE=1 bun --conditions=source apps/client/testing/performance/ui-response.ts
BENCH_VIEWS=1000 BENCH_CPU_RATE=1 BENCH_RESTORE_RUNS=3 bun --conditions=source apps/client/testing/performance/ui-response.ts
BENCH_VIEWS=100 BENCH_CPU_RATE=4 BENCH_RESTORE_RUNS=3 bun --conditions=source apps/client/testing/performance/ui-response.ts
BENCH_CPU_RATE=4 BENCH_RUNS=3 BENCH_SCREENS=1 bun --conditions=source apps/client/testing/performance/startup.ts
```

`BENCH_CLIENT_DIST` selects a separate control build. `BENCH_PROFILE` records a diagnostic CPU profile for a single palette run; do not compare profiler-enabled timings with ordinary measurements. CPU throttling on the start-screen probe first creates a blank browser target, applies the throttle and then navigates to the application. Its default normal-CPU path is unchanged.
