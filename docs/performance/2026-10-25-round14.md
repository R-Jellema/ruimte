# Shared controls and icon chunks, fourteenth round

Measured on 2026-10-25 against Ruimte `81aba8788`, with ADE CORE `7b742950`, Bun 1.4.2, Vite 8.3.5, Rolldown 1.2.15, macOS 27.2 and an Apple M4 Max. [Raw timing samples and deduplicated resource inventories](2026-10-25-round14.json) include three fresh headless Chromium profiles per case and build. Canvas rendering is excluded.

## Retained change

The initial screen already had its own chunk group, but a workspace fetched 168 JavaScript resources. Shared controls and icons were split into many small chunks. Two later groups now collect the remaining ADE CORE/Base UI controls and Lucide icons. The initial group stays first, so its existing modules remain there. Application feature imports remain dynamic.

[Rolldown's group order](https://rolldown.rs/reference/TypeAlias.CodeSplittingGroup#priority) assigns modules to the first matching group at equal priority. The UI source directory is resolved from the installed package, supporting both the linked checkout and npm sources. No dependency changed.

The final comparison builds identical application sources with the old startup-only grouping and the retained grouping. No source file was swapped. The workspace JavaScript request count falls from 168 to 96. At the workspace-ready boundary, decoded JavaScript grows from 6,982,852 to 7,031,433 bytes, about 0.7 percent.

The delayed workspace/file fixture adds 20 ms before each JavaScript response. The start-screen probe adds 20 ms before each asset response. These are loopback HTTP fixtures with no bandwidth or CPU throttling. They expose request overhead; they do not predict Electron's `app://` startup or an HTTP/2 deployment. Local first-file timing is effectively unchanged, and warm dialog openings remain similar. The larger gains occur when separate asset responses are costly.

## Stages and rejected trials

Controls alone reduced the exploratory delayed workspace from about 802 to 652 ms and the first file from 1,019 to 870 ms. Adding the icon group reduced these to about 533 and 750 ms. The table above is a separate final matched-source batch.

Three alternatives were measured and removed:

- Extra lazy view boundaries reduced the empty workspace slightly, but delayed the first file from about 1,019 to 1,070 ms. The source changes, including a status-dot extraction, were reverted.
- A global 20 KB minimum chunk size left the workspace at 168 requests and about 802 ms. It was removed.
- A broader entries-aware merge reduced the workspace to 57 requests and about 404 ms. It increased decoded workspace code to 7.96 MB and regressed the first delayed command palette from 49.4 to 84.2 ms, despite improving Settings. Local renderer task time stayed around 170 ms. This mixed result was rejected; its full six-case follow-up is retained in the raw evidence.

## Validation

Each browser case checks uncaught errors. The file case waits for actual file text, beyond the first workspace frame. Settings and the palette are opened cold and again warm. Data-saving mode disables idle prefetch so these first-use measurements remain reproducible. The file probe also records filesystem RPC timings.

The full application check and client/desktop build pass. The application unit run passes 10,443 tests; the previous functional sidebar changes passed all 391 DOM tests. Bundled development also has a separate smoke probe for Settings, the palette, editor language changes and its snippet worker. `BENCH_HMR=0` disables that probe's source-editing HMR checks so it can run without touching a person's running dev app.

The project/browser fixture is shared with the sidebar probe. Each run owns and removes its temporary daemon, projects and browser profiles. Production code changes are confined to Vite's chunk configuration.

## Reproduce

```sh
BENCH_CONTENT=empty BENCH_ASSET_DELAY=20 BENCH_RESTORE_RUNS=3 BENCH_MAX_LOAD_MS=650 bun --conditions=source apps/client/testing/performance/workspace-load.ts
BENCH_CONTENT=file BENCH_ASSET_DELAY=20 BENCH_RESTORE_RUNS=3 BENCH_MAX_LOAD_MS=900 bun --conditions=source apps/client/testing/performance/workspace-load.ts
BENCH_RUNS=3 BENCH_LATENCY=20 BENCH_SCREENS=1 bun --conditions=source apps/client/testing/performance/startup.ts
```

Use `BENCH_ASSET_DELAY=0` or `BENCH_LATENCY=0` for the local case. `BENCH_CLIENT_DIST` selects a separate control client build. Its configuration needs only the previous startup group. Run timing probes separately from builds and tests.
