# Daemon startup and file search, 25 October 2026

The second round makes remote WebRTC code lazy on the daemon, loads a requested workspace while its connection is opening, and avoids sorting all file matches for a small picker. `dev:built` also waits for daemon preparation before launching Electron. Production feature imports remain lazy.

The first round is committed as Ruimte `ad35c3583` and ADE CORE `4690b60e`. This round changes Ruimte only. Measurements use the same Apple M4 Max, Darwin 27.2.0, Bun 1.4.2, Vite 8.3.5 and linked ADE CORE checkout. [Raw samples](2026-10-25-round2-results.json) include intermediate and rejected experiments.

## Daemon and local connection

| Median | Before | After | Samples |
| --- | ---: | ---: | ---: |
| Source daemon, first successful health response | 309.1 ms | 263.8 ms | 3 / 7 |
| Source daemon, proof, ticket, protocol gate and first project list complete | 313.9 ms | 271.4 ms | 3 / 7 |
| Compiled daemon, first successful health response | 233.3 ms | 218.9 ms | 7 each |
| Compiled daemon, first project list complete | 239.1 ms | 223.5 ms | 7 each |

Each sample starts a real process with a temporary data home and an unused loopback port. It verifies the daemon's proof, exchanges the local secret for a one-use ticket, and connects through the production `LinkTransport`, socket opener and protocol gate. The secret is never printed or placed in a URL. Polling for the first health response has a 10 ms interval, so the listening measurement has that resolution.

A separate instrumented source run spent about 267 ms reaching the daemon module, followed by much smaller wiring steps. The remote peer connector imported `DirectClient` statically, which imported werift even when only a local socket was used. That import now happens inside `openPeerLink`. The existing incoming-peer implementation already loaded werift lazily. Proof/ticket/WebSocket work after listening took only a few milliseconds; it was not the main delay.

The compiled comparison builds both versions from the production entrypoints with source conditions, syntax/whitespace minification and sourcemaps. Telemetry is disabled. These are local executable measurements with empty homes, not a complete packaged Electron launch. Hooks, broker, LAN, STUN, model fetch and price fetch are disabled in all daemon probes. A repeated process reuses that series' temporary home after the first start.

The three real broker/ICE/DTLS/SCTP integration tests pass after moving the import. A separate experiment using the shell's coarse 150 ms polling cadence was noisy and did not establish a reliable additional improvement; it is retained in the raw results without a speedup claim.

## Restoring the window

The browser probe serves the real production client and opens an empty project on a real temporary daemon. It stands in for the desktop bridge, including its local secret gate. Each sample has a fresh browser profile. No canvas is rendered. The table uses a controlled 300 ms backend-preparation delay.

| Variant, 5 samples each | Page ready after navigation | Wait before navigation | Total including wait | Visible project overlay |
| --- | ---: | ---: | ---: | ---: |
| Original client | 507.4 ms | 0 ms | 507.4 ms | 5 / 5 |
| Workspace loaded beside the connection | 466.2 ms | 0 ms | 466.2 ms | 5 / 5 |
| Parallel loading plus built-dev preflight | 200.3 ms | about 301 ms | 501.3 ms | 0 / 5 |

Previously the workspace import began only after `project.open` finished, around 434 ms in this fixture. `WindowContent` now starts that same lazy import when a project starts connecting/opening, around 126 ms. It remains separate from the start screen and from optional editors, dialogs and syntax grammars. Idle start-screen prefetching still uses the existing prefetcher.

`dev:built` selects `dev:desktop:built`, which sets `RUIMTE_DEV_WAIT_FOR_DAEMON=1`. After waiting for the client server, the launcher waits for the daemon's health endpoint before spawning Electron. Its 50 ms readiness checks happen during terminal-side preparation. The existing two-minute fallback still opens the app to report a failed start. The normal `dev` command keeps its existing behavior.

The preflight removes the short connecting overlay in this fixture by putting preparation before the window; it does not make total launch time three times faster. The separate parallel-load change reduces actual page work/waiting by about 41 ms in the controlled-delay comparison. Packaged startup continues to restore windows while its daemon starts.

The visible-overlay probe checks the project-switch overlay specifically. An earlier exploratory counter also counted unrelated live status regions; those counts are not used in this table. Slow project reads or a failed connection can still display progress. The fixture demonstrates the expected built-dev behavior, not a guarantee for every saved workspace or machine.

## File search

The file benchmark compares the original source with prepared query scoring and then a best-first heap. The fixture has 100,000 paths for ranking and 20,000 or 100,000 real empty files for full `searchFiles` calls, in a temporary git repository. The listing cache is warm. Results are medians of five samples for the large fixture.

| 100,000 files, best 8 requested | Before | After |
| --- | ---: | ---: |
| Ranking, empty query | 35.50 ms | 3.70 ms |
| Ranking, `src` | 37.72 ms | 9.93 ms |
| Ranking, `project handler` | 46.61 ms | 18.92 ms |
| Full search, `src` | 52.14 ms | 46.94 ms |
| Full search, `handler` | 56.22 ms | 47.89 ms |
| Full search, `project handler` | 63.86 ms | 55.39 ms |
| Full search, no matches | 40.65 ms | 40.64 ms |

Query words are prepared once for the list. The heap visits candidates in the original ranking order and stops once enough valid paths are found. A path that disappeared still yields to the next match. Ties retain tracked-before-ignored, shorter-path, alphabetical and original input ordering. Name filtering and the realpath checks remain in the full search path.

The full-search gain is much smaller than the ranking-only gain because checking every listed name still costs time. At 20,000 files, the broad full search moved from 11.07 to 10.39 ms. This is an improvement to file picking in large projects, not a whole-application multiplier. No-match full search shows no gain.

New tests cover tied tracked/ignored matches across heap limits and filling the result limit after eight better cached files disappeared. A temporary differential probe compared 63,000 generated ranking cases against the original implementation, including Unicode, duplicate paths and edge-case limits; both produced the same checksum.

## Rejected or unchanged paths

Fetching successive 90-message backend history pages from a 30,000-message thread took about 0.07 ms. Rebuilding attach metadata was about 0.94 ms warm. No additional history cache was added there.

A trial workspace chunk reduced the restore's JavaScript requests from 168 to 16, but settings and command-palette chunks then depended on the whole 4.4 MB workspace group. It was discarded. The final chunk configuration is unchanged from the first round, and the build's start-screen guard passes.

## Reproduce

Run timing jobs sequentially, after building the client, with no competing check/build job. The daemon probe creates and removes its own homes and stops only the processes it started. It does not restart the person's daemon or open their projects.

```sh
bun run --cwd apps/client build
bun --conditions=source scripts/performance/file-search.ts
BENCH_RUNS=5 BENCH_DISK_FILES=100000 bun --conditions=source scripts/performance/file-search.ts
bun --conditions=source scripts/performance/chat-history.ts
BENCH_RUNS=7 bun --conditions=source apps/client/testing/performance/daemon.ts
BENCH_RUNS=1 BENCH_RESTORE=1 BENCH_SECRET_DELAY=300 bun --conditions=source apps/client/testing/performance/daemon.ts
BENCH_RUNS=1 BENCH_RESTORE=1 BENCH_SECRET_DELAY=300 BENCH_WAIT_BEFORE_WINDOW=1 bun --conditions=source apps/client/testing/performance/daemon.ts
```

`BENCH_CLIENT_DIST` can select a control client build. `BENCH_DAEMON_BINARY` runs a compiled executable instead of source. The compiled comparisons used these entrypoints and options:

```sh
bun build --compile --conditions=source --minify-whitespace --minify-syntax --sourcemap \
  --define 'process.env.RUIMTE_TELEMETRY=""' \
  apps/server/src/main.ts apps/server/src/fs/grep-worker.ts apps/server/src/telemetry/watchdog-worker.ts \
  --outfile /tmp/ruimte-perf-daemon
BENCH_DAEMON_BINARY=/tmp/ruimte-perf-daemon bun --conditions=source apps/client/testing/performance/daemon.ts
```

The before controls use source from `ad35c3583`. Temporary build/load plugins supplied only the original `App.tsx` or peer-connector module, without reverting files in the working tree. Baseline rendering and parallel rendering use the same current dependencies and bundler settings.

`bun run check`, the production client/desktop build, all 10,431 unit tests, 9 selected DOM tests and 3 real remote-link integration tests passed. The launcher readiness loop was also checked to wait through two failed health requests before proceeding. No ADE CORE files changed in this round.
