# Sidebar update processing, fifth round

Measured on 2026-10-25 against `d3f2df587`, on macOS 27.2 with an Apple M4 Max and Bun 1.4.2. [Raw samples](2026-10-25-round5.json) include the Bun probe, three fresh Chromium profiles per version and a separate daemon-side sidebar probe.

## Retained change

`SidebarWatch` compared two complete JSON snapshots whenever any terminal or chat status changed. A snapshot includes every project and every sidebar row. Repeated status events did the same work even when their value had not changed.

Snapshot comparison now checks state, status values and project rows separately. Unchanged arrays and project entries are recognized by reference. A changed project is compared individually. Identical status events return before allocating another status map, while still marking that status as newer than an outstanding list request.

The fixture has 20 projects with 100 rows each, 50 terminal statuses and bursts of 200 events. Each profile measures seven bursts of each kind. Every changed event must notify exactly once; unchanged events must notify nobody; the project rows must survive status updates unchanged.

| Processing 200 updates | Before, Chromium | After, Chromium |
| --- | ---: | ---: |
| Changed terminal status | 55.4 to 55.9 ms | 0.4 ms |
| Identical repeated status | 59.2 to 60.8 ms | Below 0.1 ms resolution |
| One changed project summary | 55.3 to 55.5 ms | 3.0 to 3.1 ms |

These are ranges of profile medians, not whole-application speedups. The browser executes the production watcher class and event fixtures, without mounting React. Rendering work is unchanged. The improvement removes repeated comparison work from the main thread before listeners receive the same updates.

The Bun feedback loop initially failed a 25 ms budget: changed statuses took about 44 ms per burst. Separating the comparisons reduced this to about 0.09 ms. The additional identical-status guard reduced repeated unchanged bursts from about 0.10 to 0.02 ms. Chromium confirms the effect independently of Bun's JavaScript engine.

## Correctness and rejected work

New tests verify that an unchanged event still prevents an older list response from overwriting its status. They also check snapshot identity and listener counts for equal project summaries and an actual rename. The existing watcher tests still cover reconnects, polling, partial reloads and disposal.

A separate `ProjectStore.sidebar` probe creates and saves 20 projects with 100 views each, closes them, creates a fresh store and warms its index. The first list took about 4.85 ms; subsequent lists had a median of about 1.81 ms. No extra document cache was added there: this fixture does not identify backend sidebar loading as the bottleneck, and a cache would need to preserve detection of outside edits.

The full check, 10,434 unit tests and the client/desktop build pass. The changes preserve the number and content of sidebar notifications.

## Reproduce

Run timing jobs without competing builds or tests:

```sh
BENCH_MAX_STATUS_MS=25 bun apps/client/testing/performance/sidebar.ts
git show d3f2df587:apps/client/src/shell/sidebar-watch.ts > /tmp/sidebar-control.ts
BENCH_SIDEBAR_SOURCE=/tmp/sidebar-control.ts bun apps/client/testing/performance/sidebar-browser.ts
bun --conditions=source scripts/performance/project-sidebar.ts
```

`BENCH_PROJECTS`, `BENCH_VIEWS`, `BENCH_UPDATES` and `BENCH_RUNS` adjust the watcher fixture. The browser probe defaults to three fresh profiles per version; `BENCH_PROFILES` changes that count. Without `BENCH_SIDEBAR_SOURCE` it measures only the current source. Temporary browser profiles and project fixtures are removed afterward.
