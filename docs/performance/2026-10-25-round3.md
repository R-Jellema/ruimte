# Daemon startup, third round

Measured on 2026-10-25 with Bun 1.4.2, macOS 27.2 and an Apple M4 Max. The reference is `d30bdf194`. Raw samples are in [2026-10-25-round3.json](2026-10-25-round3.json).

## Results

The compiled daemon now loads embedded ESM bytecode instead of compiling its JavaScript on every start. Hardware detection runs alongside the stores. The desktop shell checks readiness every 25 ms instead of 150 ms.

| Sequential experiment | Before | After | Samples per version |
| --- | ---: | ---: | ---: |
| Embedded bytecode, first authenticated project list | 209.82 ms | 106.62 ms | 7 / 7 |
| Start hardware detection alongside the stores | 106.62 ms | 96.20 ms | 7 / 9 |
| Shell readiness interval, with the optimized daemon | 155.49 ms | 107.57 ms | 9 / 9 |
| Complete change, newly compiled and re-signed binaries | 214.00 ms | 98.44 ms | 9 / 9 |
| Complete change, 20 stored projects | 231.68 ms | 102.71 ms | 7 / 7 |
| Hardware detection in source mode, matched loader instrumentation | 293.48 ms | 282.64 ms | 7 / 7 |

These are medians from fresh processes. The complete compiled comparison improves by 54%; the 20-project fixture improves by 56%. Each process proves possession of its local secret, mints a local ticket, completes the client transport's protocol handshake and answers `project.list`. Readiness alone is not the endpoint of the measurement.

The shell interval experiment uses the daemon harness with the same polling interval as the shell. It isolates readiness detection and authentication; it is not an Electron end-to-end launch measurement. Only readiness polling changes in the desktop code. The proof, ticket and protocol checks still run.

The 20-project fixture is seeded through `project.open` during an untimed daemon run. Timed runs reuse that persisted home, and the harness verifies that all 20 projects return after every restart. It does not contain large chat histories or active sessions.

## First use of a new executable

The first process of each newly compiled and re-signed binary was much slower than subsequent processes. In the complete comparison, those first observations were 998.73 ms before and 868.02 ms after. The remaining eight runs had medians of 213.90 and 97.94 ms. A single first-use observation per binary is not enough to claim a stable percentage for installation-time startup.

A separate instrumented first launch spent about 886 ms from spawn to the project list, while the daemon's last startup marker reported about 123 ms of process uptime. Much of that first-launch delay happens before the instrumented application initialization. This round does not establish its exact runtime or operating-system cause. It also does not clear the operating system's disk cache between samples.

Bytecode increases the standalone executable from 79,725,920 to 104,021,600 bytes, about 23.2 MiB. Native helpers are unchanged. The timing builds are silent local compiles with no release telemetry initialization; release telemetry and other platforms still need their own measurements.

## Diagnosis and changes

The benchmark's 150 ms budget failed before the changes and passes afterward. The ranked hypotheses were JavaScript compilation, eager module initialization and serial initialization waits. The bytecode experiment accounts for most of the improvement. Instrumented runs then identified hardware detection in handler registration as a remaining serial wait of about 14 ms.

`apps/server/scripts/compile.ts` adds `--bytecode --format=esm`. The explicit ESM format preserves top-level await and dynamic imports; bytecode otherwise defaults to CommonJS. Bun documents standalone ESM bytecode in its [bytecode guide](https://bun.sh/docs/bundler/bytecode). Feature imports retain their existing lazy boundaries. The build generates the bytecode with the same Bun runtime embedded in the executable.

`startDaemon` starts `readMachineModel` beside the existing CLI capability probe and store loading. Handler registration awaits that same promise before installing `server.hello`. The hardware result is ready before the server accepts clients. Port-occupancy checks still happen before `startDaemon`, and project indexing, move repair and hidden-chat pruning still complete before the socket listens.

`apps/desktop/src/main/service.ts` reduces only the readiness interval to 25 ms. A daemon that has already become ready no longer waits as long for the shell's next probe.

An initial source-mode comparison used a loader plugin only on the reference and was excluded. The source numbers above use matching loader interception on both sides. CPU profiler runs and phase instrumentation are diagnostic evidence, not timing comparisons.

## Validation

- `bun run check` passed.
- `bun run test` passed: 10,431 tests, no failures.
- `bun run build` passed for the client and desktop.
- The packaged integration test passed with the production compiler. It runs the Node launcher, starts a real daemon, exchanges a local ticket, opens a project and checks a known line through `fs.grep`. The daemon has an empty `PATH`, forcing the worker embedded in the executable rather than ripgrep. This covers runtime module and worker loading beyond the previous version-only check.
- The real remote peer integration passed: 3 tests, no failures.
- The performance harness typecheck and formatting check passed after adding the stored-project fixture.

No timing assertion was added to the ordinary unit suite. The real-process harness owns the startup budget.

## Reproduce

Run timings sequentially without competing build or check jobs. The harness uses temporary homes and stops only its own processes.

For a production compile on this machine, including native helpers:

```sh
bun apps/server/scripts/compile.ts --outdir /tmp/ruimte-round3-production
BENCH_RUNS=9 BENCH_MAX_STARTUP_MS=150 \
  BENCH_DAEMON_BINARY=/tmp/ruimte-round3-production/ruimte \
  bun apps/client/testing/performance/daemon.ts
BENCH_RUNS=7 BENCH_PROJECTS=20 BENCH_MAX_STARTUP_MS=150 \
  BENCH_DAEMON_BINARY=/tmp/ruimte-round3-production/ruimte \
  bun apps/client/testing/performance/daemon.ts
```

The timing binaries used the same daemon and worker entrypoints, source conditions, whitespace/syntax minification and source maps, without building native helpers:

```sh
bun build --conditions=source --compile --bytecode --format=esm \
  --minify-whitespace --minify-syntax --sourcemap \
  --define 'process.env.RUIMTE_TELEMETRY=""' \
  apps/server/src/main.ts apps/server/src/fs/grep-worker.ts \
  apps/server/src/telemetry/watchdog-worker.ts \
  --outfile /tmp/ruimte-round3-timing
codesign --sign - --force /tmp/ruimte-round3-timing
BENCH_RUNS=9 BENCH_DAEMON_BINARY=/tmp/ruimte-round3-timing \
  bun apps/client/testing/performance/daemon.ts
```

The reference used `d30bdf194` source without the bytecode and format flags. For a source-mode measurement, omit `BENCH_DAEMON_BINARY`. Set `BENCH_POLL_MS=150` or `25` to compare readiness intervals. `BENCH_PROJECTS` cannot be combined with the browser restore fixture, which needs a fresh empty home for each run.
