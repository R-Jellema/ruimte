# Application performance measurements, 25 October 2026

The retained changes remove a request waterfall, stop a projects-list refresh from blocking an opened project, preserve virtual-row measurements during scrolling, and reuse syntax tokens when a code block returns to the viewport. Canvas rendering was outside this investigation.

Production still loads workspace features, editors, syntax grammars and other screens through their existing dynamic imports. Vite's bundled dev mode is a separate development setting. It compiles ahead to avoid paying compilation costs on the first screen opening.

## Environment and method

Apple M4 Max, arm64, Darwin 27.2.0, Bun 1.4.2, React 19.3.0. ADE CORE uses local source links, with 32 consumers. Base revisions:

- Ruimte: `1bc703206adfd89ffda4d99388116ce1f71439ca`
- ADE CORE: `24f6aa14c1bef0288cc9cd9a64eb3802d97257b7`

The isolated application comparisons used Vite 8.3.0 and Rolldown 1.2.9. The subsequent dev-mode comparison and final production checks used Vite 8.3.5 and Rolldown 1.2.15. Raw samples and their stages are in [2026-10-25-results.json](2026-10-25-results.json).

Browser measurements use headless Chrome with a fresh profile per cold sample. Startup means the renderer's first start-screen button and its next animation frame. It does not include launching Electron or starting the daemon. Dialog measurements stop at the first frame containing the dialog, not the end of its animation. Dialog runs disable speculative prefetching to keep the cold comparison repeatable.

Results below are medians. Browser timing varies between batches, especially for small dialogs. Synthetic transport and asset delays are stated explicitly; they are not measurements of a person's network or machine.

## Isolated application changes

| Change and measurement | Before | After | Samples |
| --- | ---: | ---: | ---: |
| Group initial static modules, start with 20 ms asset delay | 907.9 ms / 225 JS requests | 163.3 ms / 8 requests | 9 each |
| Group/parallelize English locale loading, final chunk settings held fixed | 278.2 ms / 31 requests | 161.4 ms / 8 requests | 9 each |
| Dutch plus English fallback, same locale comparison | 403.5 ms / 60 requests | 188.1 ms / 14 requests | 9 each |
| Deduplicate Zod and Zustand, decoded initial English JS | 2,402,787 bytes | 2,306,856 bytes | 9 each |
| Project opening, synthetic 50 ms per transport request | 102.26 ms | 51.17 ms | 11 each |
| Revisit 20 code blocks of 80 lines, syntax work only | 47.09 ms | 0.27 ms | 10 warm passes each |
| Scroll a 30,000-message timeline, main-thread task time over 90 scroll steps | 2,086.12 ms | 1,714.75 ms | 5 each |

The chunk and locale comparisons are separate experiments, not additive savings. The first groups only the entry's static dependency graph. Dynamic feature imports remain separate. Locale JSON remains split by namespace in source and is emitted as one lazy bundle per requested application language. The requested language, English fallback and library locales load concurrently. Completed loads are reused; failed loads can retry.

Deduplication saves 95,931 decoded bytes. Its local latency samples were 120.9 and 123.1 ms, so there is no demonstrated latency gain from that change alone.

`ProjectClient.open` previously awaited `project.list` after receiving the complete opened project. Refresh now continues in the background. A held-list regression test failed on the original code and passes after the change; it also checks that the list eventually arrives.

Virtual rows previously received a new `getItemKey` callback on every render. That invalidated the virtualizer's measurements during scrolling. The callback is now stable while rows stay the same. The virtualizer also owns prepend anchoring through `anchorTo: 'end'`, replacing the manual correction. The original 30,000-message probe lost the item being read when 90 older items were prepended. The final probe retains the same item at the same pixel offset. Appending while reading preserves that offset; appending while following the end leaves a zero-pixel end gap and the last row visible.

The syntax cache belongs to a shared highlighter, across its languages and themes. It uses a 4 MiB estimated cost budget and at most 128 entries, with least-recently-used eviction. Grammar continuations bypass the cache; language/theme namespaces keep results separate. Tests check real Shiki multiline state after remounting. The cold pass was 88.7 versus 93.5 ms; the demonstrated win is repeated tokenization, not first highlighting or total chat render time. A 5 ms warm-work budget fails on the old highlighter and passes on the new one. A smaller trial cache thrashed with this fixture and was discarded.

The final English start makes 8 JS requests for 2,349,914 decoded bytes; Dutch makes 14 for 2,587,433 bytes. The newer bundler adds about 43 KB relative to the earlier optimized build. The production build guard still rejects workspace-only code in the entry's static preload graph.

## Vite bundled dev

The project already used Vite 8.3.0, newer than the [8.1 announcement](https://vite.dev/blog/announcing-vite8-1). Enabling bundled dev on the original lockfile reproduced `__rolldown_runtime__.requestLazy is not a function`. Updating Rolldown alone produced another runtime mismatch. Vite 8.3.5 with Rolldown 1.2.15 passes. The [Vite 8.3.2 release](https://github.com/vitejs/vite/releases/tag/v8.3.2) documents the fix to serve the runtime from the installed Rolldown.

All three modes below use those same updated dependencies and application sources. Each mode has three fresh Vite caches and browser profiles. The persistent React Compiler cache is warm in all modes. The first-navigation clock includes the bundled-dev bootstrap/loading page and any automatic reload, not just the final document's performance clock.

| Dev measurement | Unbundled | Bundled, lazy compilation | Bundled, compile ahead |
| --- | ---: | ---: | ---: |
| First navigation | 4,795.8 ms | 1,390.5 ms | 1,671.3 ms |
| First manual reload | 300.6 ms | 759.4 ms | 167.5 ms |
| Next warm reload | 198.4 ms | 163.6 ms | 98.9 ms |
| Settings first opening | 34.5 ms | 192.0 ms | 34.6 ms |
| Command palette first opening | 32.3 ms | 180.7 ms | 30.8 ms |
| Local source HMR | 298.0 ms | 247.5 ms | 249.3 ms |
| Initial document resource requests | about 1,251 | 29 | 16 |
| Initial decoded resource bytes | about 58.0 MB | 24.3 MB | 24.3 MB |

Compile-ahead bundled dev is the retained default. It spends about 281 ms more on first navigation than bundled lazy compilation, avoids its first-screen penalty, and halves warm reload time relative to unbundled dev. HMR timings are small-sample results, not a guarantee for every edit.

This configuration applies only while serving dev. Production retains lazy feature loading. `RUIMTE_BUNDLED_DEV=0 bun run dev:client` restores the unbundled server when investigating a plugin issue. Bundled dev is still an upstream experimental feature.

Local HMR kept page identity, including updates to linked `@adecore/ui` TypeScript and a newly introduced Tailwind arbitrary class whose computed style was checked. Linked HMR took a median 328.8 ms across three compile-ahead runs. A separate smoke check loaded the real editor and chatcomposer, changed English/Dutch labels without remounting the editor, and exchanged a request/reply with the real snippet worker. No browser runtime errors were recorded.

## Reproducing the measurements

Run from the Ruimte root with the sibling ADE CORE checkout linked. The highlighter and timeline changes are local changes in that checkout; they have not been published to npm. Build before running the production browser probes. Run timing jobs sequentially without another build competing for CPU.

```sh
bun scripts/adecore.ts status --brief
bun run --cwd apps/client build
bun apps/client/testing/performance/startup.ts
BENCH_LANGUAGE=nl BENCH_LATENCY=20 bun apps/client/testing/performance/startup.ts
BENCH_LATENCY=20 BENCH_SCREENS=1 bun apps/client/testing/performance/startup.ts
bun apps/client/testing/performance/project-open.ts
BENCH_MAX_WARM_MS=5 bun apps/client/testing/performance/chat-code.ts
BENCH_ITEMS=30000 bun apps/client/testing/performance/timeline.ts
BENCH_RUNS=3 BENCH_SCREENS=1 bun apps/client/testing/performance/dev.ts
BENCH_RUNS=3 BENCH_BUNDLED=1 BENCH_SCREENS=1 bun apps/client/testing/performance/dev.ts
BENCH_RUNS=3 BENCH_BUNDLED=1 BENCH_EAGER=1 BENCH_SCREENS=1 bun apps/client/testing/performance/dev.ts
BENCH_BUNDLED=1 BENCH_EAGER=1 BENCH_LINKED_HMR=1 BENCH_FEATURE_SMOKE=1 bun apps/client/testing/performance/dev.ts
```

The dev probe selects its mode explicitly, independently of the default config. Its HMR probes temporarily edit and restore `StartScreen.tsx` and, with `BENCH_LINKED_HMR=1`, the linked UI `Button.tsx`. Avoid concurrent edits to those two files while running it. The probe's socket proxy targets an unused loopback port, so it does not open a person's projects or sessions.

For before/after comparisons, restore only the relevant source changes from the base revisions in an isolated checkout, with the dependency versions for the intended measurement stage. Do not compare dev React timings against production React timings. The startup probe serves built assets without caching; the dev probe deliberately measures browser-cache reuse on later reloads.

## Validation and limits

`bun run check` passed, including workspace types, generated contracts, lint and formatting. The full Ruimte suite passed with 10,429 tests before the Vite patch update. After that update, the production build and full check passed again, followed by 76 affected unit tests and 7 DOM tests. ADE CORE's agents-react typecheck and suite passed with 1,192 tests, 48 skipped and no snapshot changes. The final benchmark scripts also pass the client typecheck.

This covers renderer startup, project-open coordination, settings, the command palette, editor/composer compatibility, syntax revisits and long chat timelines. It does not measure every application screen, daemon cold start, real remote-history I/O or every device's scroll frame rate. The timeline stress fixture contains user messages; syntax work is measured separately with real Shiki. No blanket frame-rate or whole-application speed multiplier is claimed.
