# Peering (this machine as the one that is worked in)

The invariants of this folder. The repository root's `CLAUDE.md` has the map and the rules that hold everywhere; `docs/reports/private/0.19.0/plans/remote-machine.md` (sections A and S) is the design. "A" is the machine whose person works on another machine, "B" is this one.

- B decides what A may do here, and nothing is granted without a link a person made on B (`links.ts`, `$RUIMTE_HOME/peers/<machineIdA>.json`). A link names one project of B per machine A and a mode ceiling, `supervised` until a person chooses another. Only a client acting as a person changes it (`peer.bind`, `peer.setCeiling`, `peer.unbind`); an agent has no socket.
- A peer is never an owner. What only the local secret may do stays with the local secret, and no `fs.*`, `bytes.read`, `session.*`, `chat.*`, `launch.*`, `project.*`, `device.*`, `browser.*`, `database.*`, `computer.*` or `auth.ticket` request is on a peer's list. A peer never gets an HTTP ticket.
- The folder, the mode and the depth are B's own: the project is the one the link names, `--cwd` stays inside that folder or its worktrees (`startCwdGuard` at every start), the mode is the narrowest of what A asks, A's ceiling and the link's ceiling, and the depth is `max(1, depth A gives)`, refused above B's maximum. B takes what A states only when it is narrower than its own bounds.
- Everything a peer starts runs as `actor: 'agent'` with B's own `start-agent` entry and lineage record (`openedBy` = `peer:<A>:<parentNodeId>`). A launch in such a chat stays held until a person approves it through B. Worktrees go under B's worktree folder. A peer drives no device.
- The nodes of A that live on B sit on one hidden, private canvas per machine A, `peer-<machineIdA>` (`peerCanvasId`), with A's node ids so session and chat ids match on both sides. Whether a canvas is hidden follows from a link and is laid over the document (`withHiddenCanvases`), like the machine of a node: it is written to neither project file, and a canvas that is hidden cannot be shared. The window of that machine mirrors its nodes onto the canvas with `peer.placeNodes` and manages only the ids it placed (recorded in the machine's file under `peers`); a node of a task (peer lineage) or one a person placed is never rewritten or ended by it, and `peer.taskStart` takes over only a node that window placed or a new one. Where a task runs here is recorded beside it, and the result is read from that record, never from the project file.
- A bundle from A is data. It goes through `git bundle verify`, and only its one `refs/ruimte/handoff/*` ref is fetched, into `refs/ruimte/received/<id>`, with hooks off in every git call that follows (the fetch, `update-ref`, `worktree add`). That ref is deleted once the worktree or the `refs/remotes/ruimte-<machine>/<branch>` ref exists, and nothing the bundle carries moves a branch a person has checked out.
- Unlinking ends the nodes of that machine here (`end-children` on the hidden canvas's nodes), removes the canvas and the link. Revoking the session of a machine closes its channels and puts its peer key on the revoked keys, which no later statement undoes.
- A machine gets in as a peer on a statement the address book signed for it (`checkPeerStatement`, ten minutes, its own signing prefix). Its record in `auth.json` has `origin: 'peer'`, never `statement`, so an older daemon drops it instead of keeping a machine as a client. A peer is not an owner, gets no ticket (`Handshake.redeemChannel`, and `ticketAccess` refuses a peer's session), and subscribes to no event (`connectionOpener`).
- The dispatcher refuses a peer every request outside `{ peer: true }` as `forbidden`, before the payload is parsed, and `register` throws on `owner` together with `peer`. Add a request to the list only after asking what a lying machine could do with it. `endpoint.info` names only the peer requests, and `server.ping` is on the list so the channel can be pinged.
- Every `peer.*` request a peer may ask starts with `requirePeerLinks`: without a link a person made here the answer is `peer-not-linked`.
- A peer is vouched for for 30 days after the last statement (`PEER_ATTESTATION_TTL_MS`, `attestedAt` on its record). Past that it is not paired, but the record stays under the same session so a new statement brings it back with its links; `peer.list` says until when (`attestedUntil`) and the window of the machine that works here renews it silently while a person uses the link (`apps/client/src/project/peer-renewal.ts`). The machine that works here forgets its peer key, the machines it knew and its statements when it leaves its account.
- The list a peer may ask is `endpoint.info`, `server.ping`, `peer.taskStart`, `peer.taskStop`, `peer.result`, `peer.bundlePut`, `peer.bundleRead` and `peer.close` (`handlers/peer-tasks.ts`, `peer-tasks.ts`). A machine has at most `PEER_MAX_OPEN_TASKS` (4) tasks open here; the fifth is `peer-busy`, which makes the other machine wait rather than fail the task. A machine keeps at most `PEER_MAX_BUNDLES` (2) transfers and `PEER_MAX_BUNDLE_BYTES` (512 MiB) of them in its bundle store, finished ones included, and its results have a limit of their own (`PEER_MAX_RESULT_BUNDLES`; an acknowledging `peer.result` makes none), and at most `PEER_MAX_WORKTREES` (8) worktrees from its tasks: a person removes those, and nothing here does. A start is judged under the machine's own queue, so the count is true when the next one comes.
- A task a peer gives is a task of this machine's `TaskStore` whose parent is the machine's hidden canvas (`peerCanvasId`), because the parent is a chat on the other machine and no node here. The outbox keeps such a task through `parents` while the canvas stands, `wake-parent` skips it, and the lineage record carries `peer` so the end-children cascade does not take its opener for a deleted one. Its result is owed in a `deliver-remote-result` entry (target `peer:<machineId>`, outliving any node) that stays until the machine acknowledges with `peer.result { ack: true }`; the machine is told over its own link (`peer.taskSettled`) and asks when it reconnects, so nothing here runs on a clock.
- A bundle a peer sends is kept in a store of its own per machine under `bundles/peers`, so another machine's bundle can never be fetched or read by this one. A result bundle is offered to the machine whose task it came from and to no other (`bundleRead`), and goes once it was read to its last byte.
- A task holds its project under the channel that started it, so the agent keeps the project loaded. The hold goes when that machine's last open task settles, when the channel closes and on `peer.close`, so a person on this machine can still close the project.
- Every end of a peer task that the machine did not ask for is told to it with `peer.taskSettled`: a result owed in `deliver-remote-result`, a task a person stopped or removed here, and the open tasks of a link that is unbound. A task that machine stopped itself (`peer.taskStop`) is not.
- Whatever another machine answers is read with the schema of the request (`remote/peer-reply.ts`), and the result text kept and woken with is cut to `MAX_RESULT_LENGTH`, so a lying machine gets no more than a refusal or a clipped line.
- A peer task's CLI never loads the configuration of the folder machine A sent (settings, hooks, permission rules, MCP servers), so only the person's own settings on B apply (`projectConfigFor` in `chat/chat-manager.ts`). A provider that cannot be kept from it (`ignoresProjectConfig` not `true`) and a terminal agent are refused up front by `peer.taskStart`, before a task or a worktree exists. What is untrusted is decided by `UntrustedFolders` (`untrusted.ts`): a node that machine gave a task or that an untrusted node opened (the `openedBy` chain and forks are walked, `peer` is never copied to the child), and any node whose cwd lies in a folder made from that machine's work (recorded under `$RUIMTE_HOME/peer-worktrees`, which outlives the link). Such a node loads no project configuration, never runs the after-settle task, and `agent`/`team` from it, or with such a `--cwd`, refuse the providers and terminals `peer.taskStart` refuses (`untrusted-folder`).
