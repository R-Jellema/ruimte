# Chats, forks and plans

The invariants of this folder. The repository root's `CLAUDE.md` has the map, the wire protocol and the rules that hold everywhere.

- A fork (`chat.fork`, `apps/server/src/chat/fork.ts`) copies the CLI's conversation at the click: a Claude transcript cut at the turn's `native.lastUuid` (format checked against Claude Code 2.1.273, refused otherwise) or Codex `thread/fork` with `native.turnId`. Its record is written before its node, its agent's note waits in the record's `preambles` (never on the wire), and its lineage entry has `relation: 'fork'`, so ending, capping or orphaning the original never touches it. A chat view forks into a chat view listed right after it (a node into a node, or a view after its canvas with `asView`), and a fork and its original with no canvas in common read each other through that lineage entry instead of an edge (`apps/server/src/context/fork-origin.ts`). A fork in a worktree puts its files to the tree its turn settled with (`checkpointAfter`) only in that new worktree, never in a shared folder; a fork into another CLI, or into an account whose folder does not hold the original's transcripts, copies no conversation and gets a handoff preamble instead (`chat/handoff.ts`), in a mode no wider than the original's. A fork stays on the original's account unless it names another; a fork into another CLI starts on that CLI's default account. A fork's summary is a turn of the fork with `summaryFor`; `SummaryCoordinator` only owes a `deliver-summary` outbox entry, whose handler draws the line back first and then writes the note (id `summary-<turnId>`, so it lands once) and a preamble in the original. A fork node deleted before anyone wrote in it takes its record and transcript copy along, never its worktree.
- An agent forks only a chat it opened itself (`ruimte-context fork`, `forkForAgent`), after its last finished turn and on the original's CLI, account and model. That fork is the agent's child and no sibling: its lineage entry names the agent with no `relation`, one deeper than it and with its mode as the ceiling, so it counts toward depth and the per-caller cap, ends with the agent and takes work only through `task new`, whose result wakes the agent once. The fork of a hidden agent is a hidden agent of the forking one.
- A plan belongs to a chat, never to a project: `$RUIMTE_HOME/chats/<chatId>.plans.json` beside the record (`apps/server/src/plans/plan-store.ts`), gone with the chat or a clear of it and copied by a fork. It is written as operations on item ids at the latest rev, without a base rev: every operation names an id and is refused when that id is gone, and the daemon is its only writer. An agent never overwrites a status a person set, never removes or retitles a step only a person checks or one a person checked, and never deletes a plan that holds such a check; nothing about a plan wakes an agent or schedules work.
- A bookmark belongs to a chat as well: `$RUIMTE_HOME/chats/<chatId>.bookmarks.json` (`@adecore/agents/chat/bookmark-store.ts`), hung on an item id of the chat's own thread (a message of the person or a reply of the agent, never a subagent's), gone with the chat or a clear of it. A fork copies the ones on the items it copied, so nothing past the cut. Every change sends the whole list as `chat.bookmarks` to the clients attached to that chat, and `chat.attach` carries it; a client that is not reading the thread has nothing to point one at.
- A visual belongs to a chat too: its list is `$RUIMTE_HOME/chats/<chatId>.visuals.json` and each page `attachments/<chatId>/<visualId>.html` (`@adecore/agents/chat/visual-store.ts`), so the attachment route and `bytes.read` serve it by its id, never inline on the daemon's origin. Only an agent's `visual show` adds one, to its own chat; a person or an agent can remove one. It goes with the chat or a clear of it, and a fork copies the ones its copied turns showed, plus those shown between turns until the end of the turn it was cut at, each with a page of its own. Every change goes as `chat.visuals` to the clients attached to that chat, and `chat.attach` carries the list.
- An image or a 3D model an agent attaches belongs to a chat as well: `ruimte-context chat attach` (`src/canvas/chat-verb.ts`) reads the file in the agent's own process and the daemon never opens a path. It keeps PNG, JPEG, GIF and WebP (10 MiB each) and binary glTF, USDZ and STL (50 MiB each), typed by their bytes (`chat/attachment-type.ts`), as `attachments/<chatId>/agent-<uuid>~<name>.<ext>` (`chat/agent-images.ts`, 64 per chat together), found by id with no index, so a clear or a deletion of the chat and a move that keeps its id take them along; a fork copies them under the same ids. Only an AI chat attaches, to its own thread.
- A question or an approval ends with its turn only when the CLI takes it back (`control_cancel_request`, or a Codex turn completing for a blocking request), when the process goes, or when a person stops the turn. One asked by work the CLI runs beside its turns (a background subagent, a workflow member; Claude Code 2.1.282 names the agent in `agent_id`) outlives the turn that was running: it stays pending, the chat reads `needs-you` between turns, and its answer goes back over the same `control_response`. Optional Codex questions also outlive a successful turn; an answer joins the running turn or starts a new one in the same chat, and an explicit withdrawal still closes the card. A stop turns down what the CLI still holds (`declineRequest`), so that work goes on instead of waiting on an answer nobody can give.
- A chat whose last turn stopped on a limit goes on under another account of its CLI only when a person asks (`chat.continueOn`, `chat/continue-on.ts`), never on its own. An account that reads the chat's transcripts (Codex accounts over one home, shadow homes included) takes the chat over in place, the way `chat.configure` switches it, and a turn opens at once that carries what the limited turn answered, refused (`chat-busy`) while the CLI still runs work in the background or waits on a request, since another account needs another CLI; any other account gets a fork cut after the limited turn, with the conversation handed over, and that fork's first turn opens at once. Either way the original's owed `resume-limit` lapses, so the limited turn is taken up once. After a fork the original keeps a note under that turn (`continued-<turnId>`), and no switch turned on later owes that turn a resume there again.
- A chat leaves Chats only through `chat.move` (`apps/server/src/projects/move-chat.ts`). It refuses what the Chats write (`onPlaces`) would end or orphan (`move-refusal.ts`), and everything it refuses is decided before a folder, a repository or a project is made, changes the chat's folder only once its CLI is gone (`ChatCore.relocate`), writes the target before Chats so a project places the chat at every moment, and rehomes a fork's lineage between the two writes, since `forksLeaving` on the Chats write would drop an unspoken fork's record and transcript. Each step has an undo, and a failure puts back the ones before it. A move is written down in `$RUIMTE_HOME/chat-moves` while it runs, and a stop in between is finished at the next start before the outbox runs (`move-repair.ts`), so Chats and a project never place the chat for long.
- An agent in Chats only suggests that its chat become a project (`ruimte-context project propose`, `projects/project-proposals.ts`); the verb makes nothing and refuses outside Chats. Its card holds the chat at `needs-you`, which the move's own `working` check ignores (`wiring/chat-move.ts`) for that one card, and the move lets go of that hold before it makes anything (a held chat does not relocate) and puts it back if the move fails, so a person can review it; any other wait of the chat still refuses the move.
